# Phase 3 — Expiring reservations

Goal: a reservation holds stock for a limited time. The buyer confirms it after paying, or cancels it. If neither happens before it expires, the stock goes back on sale. Without this, every abandoned checkout keeps units off the shelf for good, and a flash sale sells out to people who never paid.

## Rules

| From | Event | To | Stock |
|---|---|---|---|
| — | reserve | `pending` | decremented |
| `pending` | confirm before `expires_at` | `confirmed` | unchanged |
| `pending` | cancel | `cancelled` | returned |
| `pending` | `expires_at` passes | `expired` | returned |

Every other transition is refused. A unit is returned **exactly once**, whichever of cancel or expire gets there first, and a confirmed reservation is never expired.

Expiry uses the database clock (`now()`), not the clock of the instance: two instances with skewed clocks must agree on what has expired.

## Expected layout

```
db/schema.sql                    ← reservations table
internal/inventory/              ← Reservation, its status and the new sentinel errors
internal/postgres/
    store.go                     ← Reserve returns a Reservation; Confirm, Cancel
    expirer.go                   ← ExpireDue: one batch of expirations
internal/expiry/                 ← the worker loop around ExpireDue
internal/httpapi/                ← confirm and cancel routes
cmd/api/main.go                  ← starts the worker and shuts down gracefully
```

---

## Day 1 — Schema and domain

1. A `reservations` table: `id` (UUID, generated by the database), `sku` (foreign key to `products`), `quantity` (`CHECK (quantity > 0)`), `status` (`CHECK` against the four values), `expires_at`, `created_at`.
2. An index that serves the expirer's query: pending reservations ordered by `expires_at`. A partial index (`WHERE status = 'pending'`) keeps it small, because only pending rows are ever looked up by expiry.
3. In `inventory`: a `Reservation` type, its status, and `ErrReservationNotFound` and `ErrReservationNotPending`.

The in-memory store stops here. Implementing every rule twice, once in Go and once in SQL, buys nothing now that the service runs on Postgres. Phase 1 stays in the history and in its notes. The `httpapi` tests move to a small fake store that returns what each case needs.

## Day 2 — Reserve creates a reservation

1. `Reserve` takes a TTL and returns a `Reservation`. The stock update from Phase 2 and the `INSERT` into `reservations` run in **one transaction**: a reservation without its stock decrement, or the other way around, must be impossible.
2. Write it as one statement, a CTE that updates `products` and inserts into `reservations` only if the update changed a row. One round trip, and no lock held between them.
3. `POST /reservations` answers `201` with `id`, `sku`, `quantity`, `status` and `expires_at`. The TTL comes from configuration (`RESERVATION_TTL`, default `10m`).

The concurrency test from Phase 2 keeps passing, and also checks that there are exactly 100 rows in `reservations`.

## Day 3 — Confirm and cancel

1. `Confirm(ctx, id)`: `UPDATE reservations SET status = 'confirmed' WHERE id = $1 AND status = 'pending' AND expires_at > now()`. No row changed: read the reservation to tell `ErrReservationNotFound` from `ErrReservationNotPending`.
2. `Cancel(ctx, id)`: moves `pending` to `cancelled` **and** returns the stock, in one statement.
3. Routes `POST /reservations/{id}/confirm` and `POST /reservations/{id}/cancel`: `200` with the reservation, `404` for an unknown id, `409` when it is not pending. An id that is not a UUID is `404`, not `500`.

Question to think about: why does the `WHERE status = 'pending'` make confirming twice, or confirming and cancelling at the same time, safe without any lock in Go?

## Day 4 — Expire in batches

`ExpireDue(ctx, limit) (int, error)` in `internal/postgres/expirer.go`, in one statement:

1. Select up to `limit` pending reservations with `expires_at <= now()`, `FOR UPDATE SKIP LOCKED`.
2. Mark them `expired`.
3. Add their quantities back to `products`, grouped by SKU.

`SKIP LOCKED` lets several instances run the expirer at once: each one takes rows the others have not locked, instead of waiting for them. The batch limit keeps every transaction short, even after an outage leaves thousands of reservations due.

Integration tests, with reservations inserted directly with `expires_at` in the past:

- due reservations expire and their stock comes back; reservations not yet due are untouched;
- `limit` is respected, and a second call picks up the rest;
- two `ExpireDue` running concurrently on two pools return each unit once;
- `Confirm` racing `ExpireDue` on the same reservation: exactly one of them wins, and the stock matches the winner.

## Day 5 — The worker and graceful shutdown

1. `internal/expiry`: a loop that calls `ExpireDue` on a `time.Ticker` (`EXPIRY_INTERVAL`, default `5s`), and calls it again right away while full batches come back. It stops when its context is cancelled. A failed batch is logged and retried on the next tick: it must not kill the process.
2. `cmd/api/main.go`: `signal.NotifyContext` for `SIGINT` and `SIGTERM`. On a signal, `http.Server.Shutdown` with a timeout lets in-flight requests finish, the worker stops, and only then is the pool closed.
3. Unit test for the loop with a fake `ExpireDue`: it runs on every tick, drains full batches, survives errors, and returns when the context is cancelled.

Question to think about: why close the pool last? What would an in-flight request see if it were closed first?

## Day 6 — Close

1. Two instances, `RESERVATION_TTL=30s`: reserve on one, let it expire, and see the stock come back on the other. Confirm on one, and see that it never expires.
2. Phase 3 notes in `docs/notes/`: the state machine, why the expirer uses the database clock and `SKIP LOCKED`, and what a confirmed reservation means for the stock.
3. README section for Phase 3, and the new endpoints with `curl` examples.

`make check` must pass, and CI must be green.
